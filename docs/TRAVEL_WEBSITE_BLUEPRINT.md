# 可複用旅遊手帳網站規格｜Travel Diary Website Blueprint

> **用途**：下次只要準備「每日行程表（Excel／Google Sheets／截圖）」及少量旅行基本資料，就可以交給 Codex，以本專案作為樣板快速產生新的手機優先旅遊網站。
>
> **參考基準**：本儲存庫 **2026-11-24 V3** 已合併至 \`main\` 的名古屋・高山冬日旅行手帳。這份文件是**可重用規格**，不是把下一次旅行寫死為名古屋。若程式後續更新，以當時的 \`main\` 為準，先檢查實際程式後再實作。

## 1. 目標與原則

- **手機優先、繁體中文、日系繪本風**：旅行途中可快速找到當前行程、交通、住宿及導航。
- **一個地區／連續體驗一張卡片**：例如同商圈的購物、美食、景點合併；卡片內保留每個子活動的時間、說明、個別地圖。
- **關鍵交通分開**：班機、JR／鐵路、高速巴士、轉乘，以及明確需搭乘時間的移動，獨立成交通卡。
- **不把計畫當成已預訂**：來源未確認、候選班次、營業時間、票價、最後入場和天候，要清楚標示「待確認」，不自行補數字。
- **避免過度工程**：純靜態 GitHub Pages、原生 HTML/CSS/JS；不需要 Firebase、資料庫、後端或框架。
- **編輯採 PR 流程**：新分支修改、驗證、Pull Request 審核後才合併 \`main\`。
- **公開網站注意隱私**：不得放真實訂位代號、票券 QR Code、護照、電話、私人地址或電子機票原圖。

## 2. 目前程式的檔案架構與責任

| 檔案 | 責任 | 下一次旅遊通常要改的部分 |
|---|---|---|
| \`index.html\` | 全站語意結構；固定頂端導覽、首頁插畫、航班、日期導覽、出發前待辦、行李清單 | 旅行標題／日期／航班顯示、SVG 題材、清單項目 |
| \`app.js\` | 旅遊資料 \`days\`、行程卡渲染、地圖網址、日期切換、倒數、清單本機保存、Service Worker 註冊 | **主要修改**：每日資料、路線、重點行程、出發日期 |
| \`style.css\` | 色票、字型、繪本式卡片、RWD、動畫及減少動態效果 | 原則上沿用，僅因內容而微調 |
| \`sw.js\` | 首次在線載入後為首頁與 CSS/JS 提供離線快取 | 下一個**獨立新站／新路徑**可更新 cache 名稱；版本升級須檢查快取生命週期 |
| \`README.md\` | 本機預覽與 GitHub Pages 部署方式 | 更新新旅遊目的地與使用方式 |
| \`AGENTS.md\` | Codex 四項工作原則與內容安全界線 | 應保留與遵守 |

**現有主體是多檔靜態網站，而非單一 HTML。** 下一次優先複製整個樣板，維持模組化；不必為「單一 HTML」要求而強行合併檔案。

### 目前資料結構（請先閱讀實際 \`app.js\`）

\`\`\`js
const days = [
  {
    date: '12/09',             // MM/DD；對應行程年份由網站統一決定
    weekday: '三',
    city: '新穗高・名古屋',
    title: '新穗高雪山日',
    summary: '上午賞雪，下午回名古屋。',
    stay: '飯店名稱',          // 末日可以省略
    hotelMap: '飯店地圖搜尋詞',
    sources: [
      ['官方交通資訊', 'https://example.org/official-info']
    ],
    cards: [
      {
        title: '高山 → 新穗高',
        transport: '濃飛巴士',  // 沒有交通標籤時可省略
        items: [
          ['07:40', '巴士出發', '班次待確認', '上車地點搜尋詞'],
          ['09:16', '抵達目的地', '', '目的地搜尋詞']
        ]
      },
      {
        title: '同區域景點整合卡',
        items: [
          ['10:00', '主要景點', '說明', '景點地圖搜尋詞',
            [['附近景點', '另一個地圖搜尋詞']]],
          ['11:00', '附近咖啡店', '營業時間待確認', '咖啡店搜尋詞']
        ]
      }
    ]
  }
];
\`\`\`

- \`days[].cards[].items[]\` 目前為**位置式陣列**：\`[time, name, detail?, place?, extra?]\`。
- \`extra\` 為 \`[[顯示名稱, Google Maps 搜尋詞], ...]\`，用於一張卡保留多個獨立導航入口。
- \`transport\` 供交通卡片與彩色標籤識別；\`sources\` 連官方交通／景點資訊。
- \`stay\`、\`hotelMap\` 渲染每日底部住宿資訊。
- 現有 \`renderOverview()\`、\`renderCard()\`、\`renderDay()\`、\`renderRoute()\` 負責顯示。不要在下一次旅行尚未核對程式時假設上述結構永遠不變。
- 位置式陣列與欄位命名請維持一致；若要改成物件式 schema，必須一併修改渲染及測試，不得只改一半。

## 3. 下次提供的行程表：建議欄位

**最少必要**：旅行起訖日期、每一天的日期與目的地、每個活動的時間及名稱。其餘可留空，標記待確認。

| 欄位 | 說明 | 範例 |
|---|---|---|
| 日期 | 年／月／日及星期（以正確年份重新核對） | 2027/01/10（日） |
| 預定時間 | 明確時刻、約略時段、或未知 | 09:30／下午／待確認 |
| 地區 | 城市／商圈／同一景點區域 | 大須商圈 |
| 活動／景點 | 保留原始名稱與日文店名 | 大須觀音 |
| 類型 | 交通／景點／購物／餐飲／住宿／待辦 | 景點 |
| 移動起迄 | 交通時的出發與到達地點 | 名古屋站→高山站 |
| 交通工具與班次 | 火車／巴士／班機／步行；是否已訂 | JR 候選班次 |
| 詳細備註 | 營業、預約、優惠、小吃、同行者分頭行動 | 16:30 開門（待核對） |
| 導航詞或官方連結 | 最好提供日文正式地名與官網 | 名古屋PARCO |
| 重要程度 | 必去／備選／一般 | 必去 |
| 狀態與證據 | 已訂／候選／待確認；來源日期 | 未訂，官方待查 |
| 當晚住宿 | 飯店名稱與導航資訊 | XX Hotel |

**輸入形式**：優先使用原始 Excel、Google Sheets 或 CSV；截圖也可以，但要逐格閱讀，尤其橫向的日期欄、合併儲存格、色塊與備註。掃不清楚的字不要猜。**航班電子機票僅供私下核對，不能原樣公開上站**。

### 原始行程與網站資料的分層

1. **原始資料**：使用者的最新表格為行程決策來源；保留原文、時間及未確定項。
2. **標準化資料**：每個活動先形成「日期／時間／地區／類型／名稱／備註／導航／狀態」一筆。
3. **分組資料**：依同地區、連續性及活動關聯轉成 \`days[].cards[]\`。
4. **網站呈現**：首頁概要、每日時間軸、交通卡、住宿卡、清單等。
5. **變更追溯**：更新時列出新增／刪除／移動／合併及仍待確認事項，方便 PR 審核。

不要直接把試算表六欄橫向原樣放入手機頁面。

## 4. Excel／截圖 → 行程卡片轉換規則

1. **辨識日期**：每一個日期獨立成一個 \`day\`；注意跨天、週次與時區，不能只憑截圖中的「DAY1」猜年份。
2. **完整抽取**：依表格行列收集時間、活動、文字備註、emoji、住宿；缺漏／模糊事項列待確認，不自行補行程。
3. **排序**：同一天依原表的時間／順序排列。未指定時間維持「上午／午後」等原文，不硬塞時刻。
4. **同區域合併**：連續的大須觀音＋大須商店街、PARCO 各館＋購物、美食＋同一商圈等，建立一張主卡，子活動保留各自的時間與 Maps。
5. **不要過度合併**：跨城市、需要訂位、重要交通轉乘、獨立大景點，不因時間相近就合併成模糊卡片。
6. **交通獨立**：飛機、JR、巴士等單獨卡片呈現起點／終點／時間／候選狀態；步行小移動可寫在同區域卡片內。
7. **候選與主選明確**：一個「主要候選」+ 其他「備選」，不能把三個車次寫成三個都確定會搭；轉乘緩衝要提醒。
8. **必去標籤節制**：只標使用者明確指定的高優先景點；不能因插畫漂亮就全數標必去。
9. **官方資訊 vs 規劃**：時間表中的「預計 16:30 開門」不是官方已確認。票價、車次、末班、最後入場／點餐等要另行核對，查不到就標記。
10. **同名場所避免混淆**：Google Maps 搜尋詞優先使用正式日文名稱＋城市／區域，不憑模糊名稱推測位置。
11. **住宿每日顯示**：當晚飯店放在每日底部，交通中若需要回飯店取行李應保留為獨立節點。
12. **不遺漏**：逐日核對轉換前後活動總數；合併卡片不等於刪除子活動。

### PR 內建議附「逐日對照表」

| 日期 | 原表活動 | 網站卡片 | 特殊處理 | 待確認 |
|---|---|---|---|---|
| D1 | 起飛、抵達、神社、餐廳、購物 | 航班／接駁／神社＋用餐／購物 | 同區域合併 | 航廈、餐廳營業 |
| D2 | 跨城交通、老街、神社 | 交通卡／古街卡／個別神社 | 獨立交通卡 | 搭車方式 |
| D3 | 巴士、纜車、JR | 三張交通卡＋雪山活動卡 | 主班次與候選分開 | 班次、風雪營運 |

以上是**轉換方式範例**，不可當成下一趟旅行的固定活動資料。

## 5. 視覺設計：目前 V3 的可複用風格

- **主題**：日系繪本／簡約和紙旅行手帳；繁體中文與手機優先。
- **色票**：和紙白 \`#FFFCF6\`、墨灰 \`#3E3A39\`、珊瑚粉 \`#F2A497\`、山吹黃 \`#F6D27A\`、水色 \`#A8D3E6\`、若竹綠 \`#B9DAA5\`。
- **字型**：Google Fonts **Huninn**，失敗時以系統字型 fallback。
- **元件**：淺底、墨灰約 3px 粗框、約 24–28px 大圓角、平塗 SVG；**不用漸層／厚重陰影**。
- **插畫**：依目的地繪製原創 SVG（地標、山景、火車、交通工具等），不直接複製卡通角色或擅用圖片。
- **頁面結構**：固定頂端選單 → 插畫 Hero＋倒數 → 航班卡 → 日期總覽／切換 → 每日時間軸 → 住宿／官方連結 → 出發前清單與行李清單。
- **標籤**：交通方式使用清楚的彩色小標籤；少量使用「必去」標記。
- **動畫**：雪花／列車少量動效、切日輕微彈跳，必須支援 \`prefers-reduced-motion: reduce\`。

下一趟不同目的地，**改插畫內容、標題、日期與資料，不要改壞統一的設計系統**。

## 6. 互動、保存、離線與限制

- **日期連結**：首頁與每日頁支援 \`#overview\`、\`#day-1\` 等深層連結，使用者可直接分享某一天。
- **倒數**：目前採 \`Asia/Taipei\` 日曆日期，出發前／出發當天／旅行期間／結束後切換文案；下一次需要改日期與必要時區設定。
- **清單**：行前待辦、行李清單使用**不同的 localStorage key**；同裝置會保存，**不同手機不會自動同步勾選狀態**。
- **新旅行複製**：更新清單 storage key 的旅行識別碼，避免沿用前一趟已勾選狀態。
- **地圖**：Google Maps 搜尋連結需正確編碼地點文字；連結需要網路。
- **離線**：\`sw.js\` 針對首頁、CSS、JS 做首載後快取。離線不保證地圖、Google Fonts、外部網站或即時交通可用。
- **改版快取**：後續版本更新時檢查快取名稱與清理策略，避免舊版滯留；測試離線開啟／重連／新版本讀取。
- **安全**：資料只放公開可揭露的行程；輸出到 HTML 的文字要妥善跳脫，外部連結使用可信 URL；勿在 GitHub 放私密資訊。
- **不做跨手機即時編輯**：依目前選定的簡化流程，行程修改由 Codex 提 PR，合併 GitHub Pages 後兩人重新整理看到同版；不引入 Firebase。

## 7. 手機與功能驗收標準（每次更新必跑）

**畫面尺寸**：320、375、390、430、768、1280px。

- 沒有**整頁水平溢出**；日期導覽可以自行水平滑動。
- 固定選單不遮住行程；長中文、日文店名與網址可合理換行。
- 行程時間／卡片標題／子活動／導航清楚；觸控區域大約 ≥44×44px。
- 六日（或實際天數）導航、首頁卡片與深層連結正常。
- 同區域子活動均完整顯示，Maps 連結均有合理搜尋詞。
- 交通主選與候選清楚區分；未驗證票價與開放時間仍有提示。
- 倒數在目標時區午夜正確切換；旅行前後狀態正確。
- 待辦與行李勾選可各自保存；舊版升級時評估資料相容性。
- \`prefers-reduced-motion\` 正確停止非必要動效。
- Google Fonts 載入失敗仍可用；低速網路及首次載入後離線重開可用。
- GitHub Pages **專案子路徑**（如 \`/nagoya-2026/\`）的相對 CSS/JS/SW 連結正常。
- 至少截圖：手機首頁、最密集的 2–3 天、行李清單、桌面首頁。
- 清楚回報哪些是「自動測試通過」、哪些「實際外部網站無法驗證」。

## 8. 下次旅行的標準工作流程

1. **新增旅行專案**：以本 repo 為 Template／複製樣板到新 repo；不建議直接覆蓋歷史名古屋網站。
2. **提供資料**：上傳行程表（最好有原始 Excel／試算表）、日期、目的地、住宿、交通與必去清單；電子票券只供核對，不放公開 repo。
3. **先轉換、再設計**：Codex 逐日擷取與標準化活動，列出同區域分組與尚待確認事項，然後填入 \`days\`。
4. **套用繪本風格**：保留 UI 架構，更新 SVG 地標與旅遊標題、日期、航班卡、倒數、清單。
5. **驗證**：以原始表逐日逐項比對；跑 RWD、深層連結、localStorage、離線／快取等測試。
6. **送 PR**：新分支 → Commit → PR；**不要直接合併 main**。
7. **人工確認**：查看手機截圖，檢查移動與營業時間；確認後合併 PR，Pages 自動部署。
8. **旅行中更新**：只要告訴 ChatGPT 哪天哪張卡需改，重新產生給 Codex 的差異指令即可。
